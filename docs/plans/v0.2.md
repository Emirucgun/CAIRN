# Plan — v0.2 Summaries (bring your own key)

Status: **draft, waiting for approval** · 2026-11-27

Goal: tick the six v0.2 boxes in SPEC §Roadmap. That means optional 1–3 sentence summaries for files and folders, from the user's own API key, never on by default, always estimated and confirmed before money is spent, plus `cairn stats`.

Out of scope: records, the MCP server and the savings footer (v0.3); `pack` (v0.4).

## 1. Acceptance criteria → how each is met

| v0.2 box | Done when |
| --- | --- |
| Summarizer interface: Anthropic, OpenAI-compatible (base URL), optional Ollama, fake provider; keys only from env | Each provider passes a contract test against a local mock HTTP server (no network in tests). A missing key fails with the env var's name and never prints a value. |
| Lazy bottom-up file and folder summaries keyed by content hash and generator id | `cairn summarize <path>` builds only what is missing, bottom-up. A second run makes 0 calls. |
| Call cap; file count, token and cost estimate with confirmation before every run; per-repo consent | Tests cover each path: dry-run, confirm yes/no, `--yes`, missing consent with no TTY, cap exceeded, and consent re-asked when provider or host changes. |
| Secret scan before every summarizer call | Every request body passes `scanForSecrets`. A hit skips that file, logs a warning without the matched text, and sends nothing. |
| `cairn stats` reads `stats.jsonl` | Totals per command, agent and day, plus summarizer spend, with `--since`. |
| Editing one file at depth 3 triggers exactly 4 summary calls | Test with the fake provider: edit `a/b/c.ts`, re-run `summarize`, and count exactly 4 calls (`c.ts`, `a/b`, `a`, root). |

## 2. Dependencies (need your OK)

| Package | Kind | Why |
| --- | --- | --- |
| `@anthropic-ai/sdk` | runtime | The Anthropic provider. Anthropic's own guidance is to use the official SDK in a TypeScript project rather than hand-rolled `fetch`. It also brings typed errors, built-in retries on 429/5xx/529 with `retry-after`, and timeouts. |

- The OpenAI-compatible and Ollama providers use Node's built-in `fetch`, with no OpenAI SDK. Ollama serves the OpenAI chat-completions API at `http://127.0.0.1:11434/v1`, so it reuses the same code.
- **No `js-tiktoken`** (see Q2).

## 3. Design

**When the LLM is called.** Only `cairn summarize [path]` makes LLM calls. `map` and `context` show summaries that are already cached and never trigger calls, so they never prompt, spend or stall. When a summary is missing they print one hint line, e.g. `12 folders have no summary: cairn summarize src`. This is how I read SPEC algorithm 2 step 3 ("computed only when a command needs them"); see Q4.

**Which files get a summary** (proposal, Q3):
- files in the six supported languages, from skeleton + first `source_lines` lines (default 200, SPEC algorithm 2 step 4)
- Markdown files named `README*`, from their first `source_lines` lines

Other files appear in folder prompts by name only. Files skipped for size, binary or a secret are named with the reason and never sent.

**Bottom-up plan.** For the target path:
- walk the snapshot tree and collect each file and folder that has no summary entry for its hash and generator
- order the work leaves-first, and memoize by key, so an unchanged subtree costs one cache read
- a folder prompt holds only its children's summaries and skeleton names, never source (SPEC algorithm 2 step 5)
- the path's ancestors up to the root are included, which is what makes "depth 3 → 4 calls" hold

**Summary cache entries.** Spec format: `layer: "summary"`, with the generator `<provider>/<model>@p<prompt-version>`.
- **File entries** carry the skeleton they were built from.
- **Folder entries** list `children`, and also carry each child's summary text, so `map` reads one entry per folder for both the folder and its files (Q5). Per-file summary reads would bring back the 9,000-file warm-map cost we removed in v0.1.

**Failures.** A failed call (after the SDK's retries), a refusal or a truncated response marks that file as failed. Its ancestors are not built, because a folder summary keyed by its tree hash must never be cached missing a child. The run reports what failed, and the next run resumes from the cache.

**Requests.**
- Prompt `p1`: plain text, at most 3 sentences, no Markdown, and "describe only what the code shows".
- Anthropic: effort `low` and `thinking` omitted (valid on every current model), with `max_tokens` 2,048 so thinking can't truncate the answer.
- OpenAI-compatible: `max_tokens` 300.
- Concurrency comes from `[summarizer] concurrency` (default 4).

**Estimate, confirm, consent** (SPEC §Summarizer, unchanged):
- Input tokens are estimated locally as `chars / 4` × the model factor. Anthropic's exact `count_tokens` endpoint would send code to the API before the user consents, so it is never used for estimates.
- Output is estimated as 150 tokens per call, plus a thinking allowance for Anthropic, and labelled as an estimate.
- Cost uses the built-in price table (Q6) or the `price_*` settings, else "cost unknown".
- The run asks `Proceed with N calls (~X in / ~Y out tokens, ~$Z)? [y/N]`. `--yes` skips this but never grants consent. `--dry-run` prints the plan and estimate, needs no consent, and makes no calls.
- If the planned calls exceed `max_calls_per_run`, the run refuses before asking and suggests a narrower path or `--max-calls <n>` (Q7).
- Consent is stored in `.cairn/consent.json` (schema 1: provider, host, granted_at), is asked once per repo, and is asked again when the provider or host changes. Localhost needs no consent.
- Without a TTY, a run that lacks consent fails with the "run it once in a terminal" message.

**Secret scan before every call.** `secrets.ts` gains high-precision patterns:
- AWS access keys (`AKIA…`)
- GitHub tokens (`ghp_`, `github_pat_`)
- Slack tokens (`xox[abpr]-`)
- Stripe live keys (`sk_live_`)
- Anthropic keys (`sk-ant-`), and OpenAI-style keys (`sk-…` with length rules)
- Google API keys (`AIza…`)
- JWTs
- URLs with an embedded password (`scheme://user:pass@host`)

The scan runs on the exact request body, folder prompts included.

**Where summaries show up**, always labelled as a summary with the first 7 characters of its source hash:
- in `map`, as `≈ (9f2c4e1) Creates and refreshes user sessions…`
- in `context`, for top-level folders
- `cairn read` never shows summaries: it serves exact source

**`stats.jsonl`** (schema 1, one JSON line per event; keys and source text are never written):
- `serve` events from `map`, `read` and `context`: `{ts, agent, command, served_tokens, full_read_tokens}`. `full_read_tokens` is the estimated source tokens of the files the output covers, i.e. what reading them whole would cost. Both are `chars / 4` × factor (Q2).
- `summarize` events, one per call: `{ts, agent, provider, model, input_tokens, output_tokens, cost_usd}`, using the **actual** `usage` from the API response.

**`cairn stats [--since 7d] [--agent id] [--json]`.**
- It shows tokens served against the estimated full read, as a saving and a percentage, per command and per agent, plus summarizer calls, tokens and spend.
- Writing a line costs about 0.1 ms. The file rotates at 10 MB.

**`cairn doctor`** gains checks for the summarizer settings, whether the key's env var is set (value never shown), and the consent state.

**Config additions** (spec updated first): `[summarizer] source_lines = 200`.

## 4. Commit order

1. Spec: answers to Q1–Q7, config key, stats schema, consent schema. `@anthropic-ai/sdk` added.
2. Secret patterns, with tests: every pattern caught, no false positives on ordinary code.
3. Summarizer interface, the fake provider, the OpenAI-compatible provider with Ollama, the Anthropic provider, and mock-server contract tests (retries, refusal, truncation, missing key).
4. Summary cache entries, prompt `p1` builders, the bottom-up planner, and the executor with concurrency, cap and failure handling.
5. Estimates and price table, the consent store, and confirmation (TTY, `--yes`, `--dry-run`).
6. The `cairn summarize` command, plus the **depth-3 → 4 calls** acceptance test.
7. Summaries in `map` and `context`, cache-only. Perf: warm map stays under the v0.1 targets (re-run `pnpm perf`).
8. `stats.jsonl` writer and `cairn stats`.
9. `doctor` checks, acceptance checklist `docs/plans/v0.2-acceptance.md`, and the PR.

Each command gets tests against temp repos with the fake provider. **No test calls a real API.** A manual smoke test with your own key happens only if you run it.

## 5. Risks

- **Thinking tokens on Claude 5.x models.** Thinking is on by default and bills as output, so effort `low` keeps it small. Estimates may still undershoot; the run reports actual spend from `usage` afterwards.
- **Model refusals.** A summary request can be refused (`stop_reason: "refusal"`). It is treated as a failed file, as above.
- **Large repos.** Summarizing 10,000 files with Haiku 5.5 is about 15 M input tokens, roughly $1.50 plus output. The cap (200 calls by default) and the confirmation prompt are the guard.
- **Proxies.** Node's `fetch` ignores `HTTPS_PROXY` by default, so the OpenAI-compatible provider may not work behind a corporate proxy. This would be documented, not fixed, in v0.2.

## 6. Questions before I start

These are also added to SPEC §Open questions.

- **Q1 — SDK dependency.** Add `@anthropic-ai/sdk` for the Anthropic provider (Anthropic's recommendation for TypeScript; built-in retries and typed errors), with plain `fetch` for OpenAI-compatible and Ollama? **Proposal: yes.**
- **Q2 — Token counting.** The spec says served text is counted with `js-tiktoken`. But tiktoken isn't Claude's tokenizer, so it's an estimate anyway, and it costs ~200 ms to load on every command. Claude's exact counter is an API call, which can't run before consent. **Proposal:** drop `js-tiktoken` from the spec; use `chars / 4` × the model factor for every estimate and for `stats`; record **actual** usage from API responses for summarizer spend.
- **Q3 — What gets summarized.** **Proposal:** supported-language files plus `README*` Markdown; everything else is named only, with no content sent.
- **Q4 — When summaries are built.** **Proposal:** only `cairn summarize` calls the LLM. `map` and `context` show cached summaries and a hint, and never call or prompt.
- **Q5 — Folder summary entries carry their children's summary text.** This lets `map` read one entry per folder. It is a format addition to the cache entry and would bump the cache schema to 3. **Proposal: yes.**
- **Q6 — Price table.** **Proposal:** a built-in table only for current Anthropic models, dated 2026-11-03 (Haiku 5.5 $0.10/$0.50, Sonnet 5.5 $2/$10, Opus 5.5 $4/$20 per MTok, others from the same table). Other providers use the `price_input_per_mtok` / `price_output_per_mtok` settings, else "cost unknown".
- **Q7 — Over the call cap.** **Proposal:** refuse the whole run before asking, rather than summarizing a partial tree, and suggest a narrower path or `--max-calls <n>`.
